# 团队适配包实施与验收记录

## 1. 文档用途与完成目标

本文供 Tidoc 核心维护者和执行开发的 AI 使用。目标是一次完整交付团队适配能力：其他学校、车队、实验室和社团只维护配置与模板，就能继续使用主仓库发布的软件。

本文记录 2026 年 10 月 6 日团队适配工作的目标、实施范围与验收证据。协议、持久化、解析上下文、输出、交换、工具和界面入口已有实现，完整源码全库回归已通过，预览过期响应的时序调整已通过源码检查和来源集成测试。代码存在、测试用例存在和验收通过分别记录，不能相互代替。剩余工作包括真实 UI、兼容与迁移场景、发布成品和办公软件检查，并非只差 Word。当前运行及性能记录的范围见第 23.3 节。

实现状态以 [README 状态节](../README.md#状态) 为准。架构决策见 [DESIGN](../DESIGN.md)，公开协议见[开发手册](adapters/README.md)。第 3～21 节保留目标和验收标准，第 23 节按现有测试记录覆盖范围与缺口；未标为通过的目标不视为已验收。测试总数和后续运行结果由主线程补充。

完整交付必须同时满足：

1. BITFSAE 老用户保留已有设置、材料和操作习惯，正常报账不增加必经步骤。
2. 外部团队无需修改 Python、JavaScript、SQL 和打包脚本，就能适配抬头、材料规则、收款信息、设置策略和输出文件。
3. 适配包覆盖 Word、材料 PDF、总览 Excel 和附件包，支持真正影响使用的字段与材料差异。
4. 用户安装的适配包、个人信息和历史记录不受核心升级覆盖，核心与打印组件支持明确的兼容检查。
5. 同一数据目录可以保存多个方案及其历史版本。日常只需使用默认方案；混合处理时不会串用规则和收款信息。
6. 交付可复制的示例包、机器可读的协议、开发说明、校验工具和自动验收样例。

任务按依赖拆分，全部属于本次完整实现范围。不能只交付默认值导入导出，也不能把模板、历史数据、交换协议或开发工具留到后续版本。

## 2. 改造前的基线与原因

下表描述实施前的代码基线，仅用于解释改造原因。当前实现和未完成事项见第 23 节，不以这份历史表判断现有功能。

| 位置 | 改造前行为 | 改造原因 |
| --- | --- | --- |
| `tidoc/engine/validator.py` | 内置北理工两个抬头，以模块全局变量保存当前抬头配置 | 多方案、历史重识别和多个 API 实例会共享配置；需显式传入规则上下文 |
| `tidoc/engine/parser.py` | 部分 PDF 识别辅助逻辑调用 `supported_titles()` | 修改校验器不足以解除全局依赖，解析辅助也需接收上下文 |
| `tidoc/db/entries.py` | 材料要求保存在全局 `meta`，齐备计算识别固定几类材料 | 需支持条目自己的规则、自定义材料和条件要求 |
| `tidoc/api.py` | 启动及修改材料要求时调用 `_sync_entry_statuses()`，遍历全库 | 不能因更换默认方案重新解释全库历史条目 |
| `tidoc/db/profiles.py` | 创建报账人要求姓名和审核人都非空 | 需按方案检查审核人，姓名仍为核心要求 |
| `tidoc/services/bindle.py` | 绑定包版本为 4，按姓名与审核人复用身份 | 需处理可空审核人、规则引用、自定义字段和材料角色 |
| `tidoc/services/printing.py` | 将应用级收款信息逐字段回退到报账人信息 | 可能组成来源不同的收款信息，需改为完整收款对象选择 |
| `tidoc_print/builder.py` | 按抬头分组；同组报账说明采用首条条目的人员信息 | 需明确统一收款与按收款人拆分，禁止从第一条猜收款人 |
| `tidoc_print/word_docs.py` | 文案含机械与车辆学院、车队采购用途；按固定段落和表格位置写入 | 需用稳定模板数据与模板标记替换位置式修改 |
| `tidoc_print/models.py` | 打印附件仅含发票 PDF、付款图片和查验 PDF | 实物图及自定义材料必须能进入指定输出 |
| `tidoc/services/exports.py` | Excel 列、附件命名与类型名称固定 | 外部团队不能只适配 Word，其他交付物也需有限配置 |
| `tidoc/web/app.js` | 内置抬头简称、配色、工训楼、固定输出列表和设置默认值 | 前端应渲染后端解析后的配置，不再维护另一套业务默认值 |
| `tidoc/db/schema.py` | 当前数据库版本为 11；一个条目至多属于一个批次 | 新增规则归属时保留现有条目及批次关系 |
| `.github/workflows/release.yml` | Word 模板随打印组件打包 | 需明确内置适配资源、用户资源与独立组件的打包边界 |

现有发票导入、附件存储、批次、标签、人工修改留痕和本地交换流程继续复用。代码改造围绕配置解析、状态计算、数据投影和输出编排展开。

## 3. 总体方案与扩展边界

### 3.1 产品与技术概念

用户界面使用“报账方案”，开发文档使用“团队适配包”。一个适配包定义一种报账用途。一个团队有不同经费或不同提交要求时，可以维护多个包。

| 概念 | 含义 | 标识 |
| --- | --- | --- |
| 适配包 | 可发布的配置、模板与静态资源 | `package_id`、`package_version` |
| 本地方案 | 用户安装或复制适配包后形成的本地使用实例 | `scheme_id`，本机 UUID |
| 方案修订 | 某次包版本、设置策略和本地覆盖合成后的不可变定义 | `revision_id`，规范化内容摘要 |
| 个人资料 | 报账人身份、收款对象及其实际填写值 | 独立记录，不属于公共适配包 |
| 导出任务 | 本次选择、数据快照、分组、输出与渲染结果 | `job_id` |

一个本地方案只基于一个完整适配包。不提供运行时多包叠加、依赖解析或继承树。开发工具允许复制示例，打包结果必须独立完整。

### 3.2 必须开放的能力

| 扩展面 | 完整支持范围 | 边界 |
| --- | --- | --- |
| 单位与抬头 | 多抬头、税号、简称、语义色、默认抬头、部门与用途 | 不允许改写原始发票识别事实 |
| 设置策略 | 注册设置的默认值、可编辑性、显示方式 | 不允许任意覆盖应用 `meta` 键 |
| 附加信息 | 方案、收款对象、条目、批次、单次导出的类型化字段 | 不开放任意数据库列和界面插槽 |
| 材料角色 | 内置材料、自定义材料、格式和数量要求、显示顺序 | 自定义材料不自动获得 OCR 或税务识别能力 |
| 条件规则 | 按金额、抬头、选择字段等决定材料或字段要求 | 使用有限声明语法，不执行脚本 |
| Word | 多模板、变量、重复行、条件段落、页眉页脚、静态图片 | 不承诺任意 Word 自动排版和宏执行 |
| 材料 PDF | 按条目或材料排列、材料包含项、图片布局、编号 | 不修改原始 PDF 内容，不增加 Office 转 PDF 服务 |
| Excel | 条目或明细行、列选择、标题、顺序、基础格式与合计 | 不开放任意工作簿脚本或公式语言 |
| 附件整理包 | 分组、目录和文件名、材料选择、清单 | 路径只能使用规定变量，不能访问目录外文件 |
| 使用说明 | 方案说明、字段帮助、模板说明、作者和联系链接 | 不注入 HTML、CSS、JavaScript，不替换产品导航 |

### 3.3 保持在核心中的能力

解析算法、识别来源优先级、OCR 服务、原始数据修改留痕、重复发票判断、条目和批次生命周期、绑定包完整性检查、核心更新及组件安装均由核心维护。

报账方案可以隐藏不常用的入口，也可以规定提交材料要求。它不能取消原始数据留痕、关闭包完整性检查、跨抬头混合付款文件，或暗中触发付费识别。

“固定设置”是工作流程约束，不是权限系统。拥有本机数据和文件访问权限的人仍可复制并修改方案。本次不增加管理员、登录和权限管理。

### 3.4 明确不纳入的能力

本次不实现任意 Python 插件、网页扩展、插件市场、自动下载团队配置、审批流程引擎、多人云同步、差旅分摊、无票报销模型和跨币种会计计算。

自定义字段不挂在解析产生的物资明细行上。重识别会改变明细行身份，为这些行增加可迁移编辑记录会扩大数据模型。本次通过条目字段、完整原始明细和固定的明细展示策略满足物资报账。需要逐项资产卡片或逐项费用分摊的团队超出本工具范围。

上述边界以数据含义决定，不以“开发起来麻烦”决定。开发工具和示例要充分，但不能把适配包发展成第二套应用运行环境。

### 3.5 边界选择的依据

| 决策 | 只开放更少能力的后果 | 再扩大能力的代价 | 本计划选择 |
| --- | --- | --- | --- |
| 附加字段 | 模板需要项目编号时仍得改核心 | 任意表单和明细实体会引入新的数据生命周期 | 5 个确定作用域，共用类型化表单 |
| 材料扩展 | 审批单、合同只能混在“其他”里，无法提示缺项 | 自定义识别器需要执行代码并维护文件解析协议 | 自定义角色和要求，共用附件仓库 |
| 条件规则 | 按采购类型和金额补材料只能人工记忆 | 通用规则语言会增加调试、执行和兼容成本 | 有限条件、增加要求和提醒 |
| 输出范围 | Word 可换，Excel 和材料包仍需手改 | 自由报表平台会带来公式、布局和插件运行时 | 4 类固定输出器，各自开放具体参数 |
| 版本归属 | 换方案会改变历史状态和文案 | 多账套、多人权限和云端组织扩大产品范围 | 单库、多方案、条目固定修订 |
| 插件形态 | 只有默认值预设无法表达实际团队差异 | 任意脚本把核心内部接口变成长期兼容负担 | 声明式适配包，加真实模板与开发工具 |

主要开发工作集中在规则归属、收款模型和打印数据转换。增加一个 JSON 字段或模板标签通常不是主要成本。本计划不重做发票解析算法、主列表、附件仓库和组件更新器，以此控制整体改动范围。

## 4. 包格式与公开协议

### 4.1 文件布局

发布文件扩展名为 `.tidoc-preset`，内容为 ZIP。原有 `.tidoc` 继续表示材料绑定包。开发目录结构如下：

```text
org.example.lab/
├── manifest.json
├── scheme.json
├── fields.json
├── materials.json
├── rules.json
├── outputs.json
├── templates/
│   ├── purchase_request.docx
│   └── cost_settlement.docx
├── assets/
│   └── logo.png
└── checksums.json
```

`manifest.json` 和 `scheme.json` 必填。其余 JSON 缺省为协议规定的空集合；模板和图片按引用加入。`checksums.json` 由打包工具生成，不由作者手写。示例数据、开发提示和校验期望放在源码目录的 `examples/`，默认不进入发布包。

各 JSON 使用 UTF-8、标准 JSON，不支持 YAML、注释和运行时 include。编辑器说明通过 JSON Schema 的 `description` 提供。包内路径统一用 `/`，相对包根目录解析。

### 4.2 清单示例

以下示例展示 API 1 清单，`adapter_api` 中的 `1` 表示协议主版本，不是软件版本。

```json
{
  "format": "tidoc-team-adapter",
  "schema_version": "1.0",
  "package_id": "org.example.lab",
  "package_version": "1.0.0",
  "name": "示例实验室物资报账",
  "description": "物资采购材料整理与提交",
  "author": "示例实验室",
  "requires": {
    "adapter_api": 1,
    "capabilities": [
      "fields.v1",
      "material-roles.v1",
      "rules.v1",
      "output.docx.v1",
      "output.pdf.v1",
      "output.xlsx.v1",
      "output.attachments.v1"
    ]
  }
}
```

`package_id` 使用小写 ASCII 点分名称，长度不超过 100；字段和输出局部 ID 使用小写字母、数字和下划线，长度不超过 64。包版本使用三段数字及可选预发布后缀；客户端不手写字符串大小比较。

同一个包 ID 和版本只能对应一个内容摘要。收到同版本不同内容时判为冲突，要求作者增加版本或用户另存副本，不静默覆盖。

`requires.capabilities` 由工具根据配置和模板推导，打包时校验作者声明。缺少 Word 组件不阻止安装和使用条目管理，但对应输出显示“需要打印导出组件”。未知的字段、规则或格式主版本会阻止激活相关方案。

包摘要按排序后的“规范路径、文件字节摘要”清单计算。`checksums.json` 不计算自身，ZIP 压缩顺序和时间戳不影响逻辑内容摘要。修订摘要另对规范化有效定义及引用资源摘要计算，排除本地 UUID、安装时间和绝对路径。

### 4.3 单一协议定义

在 `schemas/team-adapter/1/` 提供 JSON Schema、注册表导出和模板数据 Schema。设置与能力由 `tidoc/adapters/registry.py` 注册；模板字段及文件名目录统一读取 `tidoc_print/context_fields.json`。注册表导出与运行时目录的一致性由测试核对。

开发手册、编辑器、打包和运行时检查使用这些公共定义。核心四类输出预检与打印 IPC 在实际运行中使用唯一的 `schemas/team-adapter/1/context.schema.json` 校验完整上下文，由 `tidoc_print.context_validation` 加载。v1 转换后的 v2、源码和外部进程执行同一检查，诊断只给 JSON Pointer 和约束，不回显私人值。纯数据、资源路径、主体隔离和模板字段权限检查继续独立执行；自动覆盖及验收边界见第 23 节。

Schema 中的重复结构通过 `$defs` 复用，`export.options` 和 `completeness` 仅开放正式属性。核心与打印组件加载同一资源，不为源码、外部进程或兼容请求维护独立定义。

使用 JSON Schema Draft 2020-12 描述公开 JSON 结构。运行时采用经过固定版本验证的校验库，核心仅因此增加实际使用的轻量依赖。工具和应用必须调用同一套校验函数，禁止维护两份近似规则。

领域检查独立执行：跨文件引用、隐藏必填项、禁用但必需的功能、模板变量、字段作用域、输出分组及能力依赖。Schema 校验通过不等于包可用。

未知正式属性一律报错；扩展备注仅允许出现在 `x_metadata` 对象，运行时不读取其业务含义。未来新增能力必须有协议定义，不能依靠“未知字段忽略”获得表面兼容。

## 5. 配置解析与设置策略

### 5.1 配置职责

`scheme.json` 保存组织信息、抬头清单、设置策略、导入默认值和默认输出选择。条目材料、附加字段、规则及输出各自有独立文件，避免一个巨型配置同时承担所有含义。

抬头项包括稳定 ID、名称、税号、简称及语义色。名称允许重复展示场景时，必须使用不同 ID 并具有可区分税号或说明；同一方案中完全相同的名称和税号去重。

语义色仅允许核心提供的有限色名。抬头判断以名称和税号事实为依据，颜色和简称不参与识别。

### 5.2 设置描述形式

```json
{
  "settings": {
    "entry.default_paid_to_invoice": {
      "default": true,
      "editable": true,
      "presentation": "advanced"
    },
    "profile.reviewer_required": {
      "fixed": false,
      "editable": false,
      "presentation": "hidden"
    },
    "print.numbering": {
      "default": true,
      "editable": true,
      "presentation": "visible"
    }
  }
}
```

`default` 与 `fixed` 互斥。`fixed` 要求 `editable=false`；可编辑设置必须有默认值或明确的空值语义。`presentation` 仅允许 `visible`、`advanced` 和 `hidden`。

注册表同时定义设置的数据类型、核心缺省值、合法范围和允许出现的作用域。适配包只能收窄允许范围，不能修改类型。布尔值必须是真正的 JSON 布尔值，不接受字符串 `"false"`。

### 5.3 开放设置清单

| 设置组 | 允许控制的内容 | 生效位置 |
| --- | --- | --- |
| 导入 | 默认抬头、实付初值是否取发票总额、建议标签 | 新建条目 |
| 身份 | 审核人显示方式、是否必填、默认使用本人或代填视图 | 身份编辑及当前条目检查 |
| 材料 | 各角色的显示、顺序和卡片快捷入口 | 材料操作及详情 |
| 输出 | 默认输出、编号、图片布局、内容排序、金额口径、收款模式 | 批次和本次导出 |
| 辅助功能 | 阿里云识别入口、查验辅助入口是否显示；付款识别入口偏好 | 当前方案的操作入口 |
| 交接 | 备注和普通标签是否默认带出 | 绑定包导出选项 |

抬头列表、材料要求和字段规则使用各自类型化定义，不再作为不透明字符串设置。`multiClaimantMode` 等视图偏好可得到一次初始化建议，但不能禁止查看或处理已经存在的其他报账人。

主题、字体缩放、数据路径、目录监听路径、OCR 密钥、网络授权、源文件清理行为、更新渠道和组件地址不允许团队包固定或修改。隐藏云识别入口不删除密钥，也不触发网络请求；网络行为沿用应用自身设置，不由适配包改变。

### 5.4 值的优先级

普通可编辑设置按“核心缺省 → 包默认 → 本地方案覆盖”合成方案修订。固定设置直接采用包内固定值，本地覆盖存在时作为更新冲突报告。

允许批次或单次导出修改的输出设置，在方案修订之后继续应用“批次覆盖 → 本次导出覆盖”。核心不变量最后检查，适配包和临时参数都不能绕过。

个人资料不进入上述覆盖链。收款信息必须选定一个完整对象，再对该对象编辑。空字符串是用户明确清空，缺少键才表示继承。列表按稳定 ID 编辑并显式删除，不使用数组下标合并。

默认输出也区分缺省和显式空列表。未配置 `print.default_outputs` 时继承 `scheme.default_outputs`，该键缺省时采用输出声明的 `default_selected`；任何明确的 `[]` 都表示全不选。本次选择和前端勾选框不得将空列表恢复成默认，完整语义见[输出说明](adapters/OUTPUTS.md#默认输出与本次选择)。

### 5.5 显示策略的约束

隐藏不等于数据删除，也不等于验证关闭。隐藏但必填的字段必须有确定值或可达的填写入口，否则包校验失败。条件隐藏的字段同样要检查条件满足时是否可填写。

历史条目存在某种材料或字段时，即使新方案隐藏该入口，详情仍提供“已有材料／历史信息”查看及维护入口。用户必须能找回原来填写或上传的内容。

## 6. 信息字段与收款模型

### 6.1 字段作用域

| 作用域 | 保存内容 | 编辑位置 | 随公共包分享 |
| --- | --- | --- | --- |
| `scheme` | 部门、用途、存放地点等公共或本地方案值 | 方案设置 | 仅被标为公共且可分享的定义与默认值 |
| `payee` | 收款人姓名、人员编号、联系方式、账户类型及账号 | 收款信息 | 仅字段定义，不含实际填写值 |
| `entry` | 用途分类、项目编号等单张发票附加信息 | 条目详情及受控批量编辑 | 定义随包，值随材料交换策略 |
| `batch` | 经费项目、提交编号等整批信息 | 批次设置 | 定义随包，值留在本地批次 |
| `export` | 文档日期、当次签署名称等临时信息 | 打印导出弹窗 | 定义随包，值记录在导出任务 |

报账人继续使用现有 `profiles`。它表示材料归属人，与收款对象分开。名字和审核人的显示规则可以配置，但适配包不能把二者重新定义成另一个实体。

### 6.2 字段定义

```json
{
  "fields": [
    {
      "id": "project_code",
      "scope": "batch",
      "label": "经费项目编号",
      "type": "text",
      "max_length": 80,
      "required_at": ["export"],
      "presentation": "visible",
      "sensitive": false,
      "transfer": "never"
    },
    {
      "id": "purpose",
      "scope": "entry",
      "label": "采购用途",
      "type": "select",
      "options": [
        {"value": "equipment", "label": "设备"},
        {"value": "consumable", "label": "耗材"}
      ],
      "required_at": ["complete"],
      "presentation": "visible",
      "sensitive": false,
      "transfer": "include"
    }
  ]
}
```

支持 `text`、`multiline`、`integer`、`decimal`、`money`、`date`、`boolean`、`select` 和 `multiselect`。支持长度、数值范围、选项集合、帮助文字、静态默认值与 `visible_when`。不支持自定义正则、公式和脚本控件。

字段命名空间为 `package_id + scope + id`。模板在已经绑定方案的上下文中使用局部名称，例如 `batch.fields.project_code`。原始发票号、金额、购买方和识别明细保留在核心命名空间，不能被自定义字段覆盖。

金额用十进制字符串，日期用 `YYYY-MM-DD`。人员编号、电话、银行账号使用字符串，保留前导零。字段类型不允许在同一稳定 ID 上改变。

`required_at` 允许 `complete` 和 `export`：条目字段可以两者兼有；批次、收款与单次导出字段只在相关输出预检时检查。草稿始终可以保存；类型错误不能作为正常值写入，旧数据异常则保留原文并提示修正。

### 6.3 收款对象与选择顺序

独立收款对象保存姓名、人员编号、电话、账户类型、开户行和账号。注册设置 `payee.personnel_number_label` 默认为“人员编号”，可设为“学号”或“工号”；BITFSAE 包使用“学号”。额外字段由 `payee` 定义补充。

支持 `personal_bank`、`corporate_bank` 和 `none` 三种账户类型，按选择显示相关字段。包提供字段要求，不随包附送真实账户信息。

输出收款模式为：

- `single`：本次分组选择一个收款对象，适合负责人统一收款。
- `by_claimant`：按报账人映射的收款对象拆分；映射缺失时预检提示补齐。
- `none`：输出不含收款段落，不要求收款信息。

选择优先级为“本次明确选择 → 批次已保存选择 → 本地方案默认收款对象”。按报账人模式只读完整映射，不按姓名猜测，不用首条记录或逐字段回退拼接一个人。

打印前展示收款对象名称和账号尾号。多个收款人的材料不得合成一份只有一个账户的付款说明；共用一个账户必须由 `single` 模式明确选择。

## 7. 材料角色与条件规则

### 7.1 存储类型和材料角色分开

保留现有附件 `type` 作为核心处理类别。新增 `role_id` 表示方案材料角色，并通过条目修订解释角色定义。

内置角色对应发票、付款截图、实物图、查验单和其他材料。自定义角色使用 `custom:<package_id>:<id>`，底层 `type=other`。例如合同、采购审批和报价单拥有不同角色，但继续使用同一附件仓库。

角色定义包含名称、说明、允许文件类型、最小／最大份数、详情顺序、卡片入口建议和是否允许用户重分类。支持 PDF、PNG、JPEG 和普通附带文件；不认识的文件仍可作为附件保存，但不能自动转成材料 PDF。

核心发票角色固定存在。发票 PDF 和 XML 都可用于日常材料齐备，但需要打印票面时另行要求 PDF。自定义角色不能替代发票，也不能借用付款 OCR 或查验单归属检查。

同一文件在同一条目仍保持一次存储和一个角色。角色调整记录历史；本次不实现同一附件同时满足多个独立材料要求。

### 7.2 条件语法

条件使用有限 JSON 表达式。组合只允许 `all`、`any`、`not`；比较只允许 `eq`、`ne`、`in`、`gt`、`gte`、`lt`、`lte`、`present`。操作数只能是白名单字段引用和类型匹配的字面量。

```json
{
  "rules": [
    {
      "id": "equipment_needs_approval",
      "stage": "complete",
      "when": {
        "all": [
          {"field": "entry.fields.purpose", "op": "eq", "value": "equipment"},
          {"field": "invoice.total", "op": "gte", "value": "1000.00"}
        ]
      },
      "require": [
        {"material": "custom:org.example.lab:approval", "min_count": 1}
      ],
      "message": "设备采购达到本方案设定金额，请补充审批材料。"
    }
  ]
}
```

金额阈值是团队自己填写的规则，不代表软件提供财务合规判断。允许引用购买方抬头 ID、发票金额、实付值、条目字段；导出阶段另可引用批次字段、收款类型和本次输出 ID。

条目齐备规则不能依赖批次、收款对象和导出日期，避免同一条目换一个打印目标就改变列表状态。规则不能读取其他条目、其他人的资料、系统路径或网络内容。

### 7.3 缺值与规则冲突

比较使用三值结果：满足、不满足、待确定。`present` 明确返回是否有值，其余比较遇到缺值时返回待确定。`all`、`any`、`not` 按三值逻辑计算，不能把缺值直接当作条件不成立。

有材料或必填效果的规则处于待确定时，列为“需补充条件信息”，该阶段不通过。普通提醒规则遇到缺值只提示待核对，不伪造通过。规则只能增加要求或给出提醒，不能删除另一条规则的要求。

要求合并采用字段集合并集、材料最小数量最大值。包声明的最大数量小于有效最小数量时拒绝安装；互斥条件无法静态判定的数量冲突，在运行时报告规则 ID 并阻止相关导出。

规则结果统一返回 `code`、`rule_id`、`stage`、`severity`、`target`、`message` 和 `suggested_action`。严重级别仅有 `info`、`warning`、`required`；规则不能覆盖核心的 `blocked` 结论。

### 7.4 状态与操作入口

保留 `draft`、`partial`、`complete` 和现有识别状态。齐备由当前条目固定修订的发票要求、材料角色、条目字段及核心阻断项共同计算。任意角色已有附件就算存在材料，避免自定义附件条目仍被判为空草稿。

“齐备”和“本次可导出”分别计算。条目齐备但缺少银行信息或发票 PDF 时，列表状态不退回，打印弹窗显示本次缺项。

卡片继续突出常用材料操作。适配包可以建议最多 4 个材料快捷入口，其余进入一个“材料”菜单；存在缺项时显示数量和具体名称。详情按材料角色分组，不增加新的功能页面。

文件夹、拖拽和粘贴导入仍采用核心识别。无法确定自定义材料角色时进入现有预览供用户指定；本次不开放文件名规则脚本，也不假装能自动理解合同和审批文件。

## 8. 稳定数据上下文与输出编排

### 8.1 输出前生成统一数据快照

`ExportContext` 将数据库记录转换成版本化纯数据。Word、Excel、附件包和 PDF 使用同一套投影规则，避免各自解释金额、姓名和字段。模板字段与文件名目录来自共享轻量资源 `tidoc_print/context_fields.json`，核心和独立组件读取同一来源。

| 根对象 | 内容 |
| --- | --- |
| `schema_version` | 模板数据协议版本 |
| `scheme` | 公共组织信息、方案字段、包和修订来源 |
| `title` | 本次分组抬头 ID、名称和税号 |
| `batch` | 批次名称、备注及当前方案命名空间内的字段 |
| `payee` | 本次分组明确选择的完整收款对象或 `null` |
| `export` | 日期、输出 ID、临时字段和选项 |
| `entries` | 排好序的条目、报账人、审核人、金额、条目字段和明细 |
| `rows` | 按输出指定策略生成的平铺表格行 |
| `totals` | 发票合计、实付合计、选定输出合计、数量及缺值计数 |
| `diagnostics` | 未识别明细、缺少单位、金额差异等预检结果 |

跨抬头总览的根 `title` 为 `null`，每个条目保留自己的完整抬头对象。跨批次总览的根 `batch` 同样为 `null`，条目携带其批次来源；这类输出不能引用单一批次字段。跨方案通用导出的根 `scheme` 为 `null`，不提供团队附加字段。

批次投影只提供 ID、名称、文本备注和当前组字段；缺失备注转为空字符串。数据库内部的 `output_settings`、`updated_at` 不进入模板上下文，批次设置先由编排器解析为当前输出选项。

附件路径只进入组件内部的资源表。模板得到角色、名称和数量，不能获得任意绝对路径、数据库连接或 Python 对象。模板需要的静态图片随 DOCX 嵌入；材料图片通过 PDF 输出处理，不提供动态图片对象接口。

上下文金额保持十进制字符串；渲染过滤器只负责显示。稳定排序支持发票日期、发票号、报账人、销售方、创建时间和原选择顺序，最后以条目 ID 保证确定性。

### 8.2 输出声明

输出类型仅有 `docx`、`pdf_bundle`、`xlsx` 和 `attachment_zip`。输出项声明 ID、显示名称、默认选中、适用条件、收款模式、分组、排序、所需字段和类型专属参数。

Word 输出的数量、名称和 ID 由包作者决定，例如 `purchase_request`、`settlement` 和 `equipment_record`。公共业务路径不要求 `reimbursement` 或 `acceptance`，也不强制两份文档。下例仅展示 BITFSAE 的一种输出。

```json
{
  "outputs": [
    {
      "id": "reimbursement",
      "label": "报账说明",
      "type": "docx",
      "template": "templates/reimbursement.docx",
      "default_selected": true,
      "payee_mode": "single",
      "group_by": ["title"],
      "rows": "invoice_summary",
      "amount_basis": "invoice",
      "filename": "{title.short_name}_报账说明_{export.date}.docx"
    }
  ]
}
```

团队输出先按本地方案和修订分组，再按下表处理抬头。可追加按报账人、收款对象或批次字段中的一个标量分类字段分组。跨批次选择时，引用批次字段的输出还必须按批次拆分。

| 输出类型 | 抬头隔离规则 |
| --- | --- |
| Word、材料 PDF | 每个文件只含一个抬头，不能取消此分组 |
| 总览 Excel | 可以保留跨抬头总览，但必须带抬头列；同名不同税号时同时带税号列 |
| 附件整理 ZIP | 可以包含多个抬头，但必须以不同主体目录隔开，并在清单中标明 |

通用输出 ID 为 `generic_overview`、`generic_attachments` 和 `generic_materials`。通用总览 Excel 与附件包支持跨方案选择。通用材料 PDF 也可处理未安装来源包的条目，但每个文件仍按真实抬头隔离。三项通用输出只使用核心字段和可解释的材料标签，不套用另一方的团队表头、收款信息或模板。

桌面本次输出、临时字段和每项输出设置按 `scheme_id:revision_id` 保存选择。两个本地副本共享修订时也互不串用；整张多方案映射不会进入单组模板上下文。

抬头组键包含规范化名称和税号；税号未知时使用稳定抬头 ID，不能仅按显示名称合并。未配置的真实购买方使用明确的临时主体键；无法确认属于同一主体时分开输出并提示核对。

批次可以继续包含不同抬头和不同方案的条目。打印弹窗根据有效修订生成分组，不让其中一个方案支配全部条目。用户可在预检中明确把选定条目重新绑定到同一方案，完成校验后合并相容分组；Word 和材料 PDF 仍不能跨抬头合并。

### 8.3 金额与明细策略

`amount_basis` 仅允许 `invoice` 和 `paid`。实付为空不等于零，按实付导出的条目缺值时阻止相关输出。任何模式都不能把实付总额写回发票总额。

表格行支持 `invoice_summary` 和 `invoice_items`：前者每张发票一行，后者逐项展开识别明细。发票级实付金额不自动按商品比例分摊；逐项输出中实付只能作为发票级上下文或独立汇总列，不能产生虚构商品单价。

缺少明细时可以使用明确标记的“发票汇总行”，包含用户核对品名和发票总额。缺单位或数量默认保留空值。包可选择兼容策略，例如 BITFSAE 使用“个”和数量 1，但需标明为输出缺省值，不写回识别结果。

不同单位的数量不得无提示相加。BITFSAE 既有按发票压缩的数量展示可作为明确的兼容策略保留，并在开发说明中注明适用前提。通用方案仅对单位一致的明细合计数量，否则留空。

### 8.4 预检和交付原子性

预检一次返回全部分组、预计文件、收款对象、缺项和诊断。隐藏输出也要经过适用条件检查，不能直接调用后端绕过。

选中的输出存在必需缺项时，默认不生成任何文件。用户可以在预检中取消有问题的输出，再生成剩余项目；不自动把失败项目略过并报告成功。

生成使用独立任务临时目录，所有文件完成并通过结构检查后，整体移动到新的导出目录。出错保留可诊断的任务记录，不在最终目录留下貌似完整的半套材料。

生成进度由实际工作更新：核对资源、核心 Excel／ZIP 生成、Word／PDF 生成、验证所有产物、原子保存。`get_export_progress(job_id)` 仅读取有界内存状态，前端每 400 ms 查询；进度及取消接口都不等待长导出占用的 `_api_lock`。核心写出器完成当前有界步骤后响应取消，组件渲染沿用取消与超时路径。无法提供细分完成数的阶段只显示阶段，不估算百分比。

初始导出记录文件保存失败时，任务标为 `failed`，诊断为 `EXPORT_RECORD_FAILED`，清理半写记录文件并使原预览失效。数据库快照和原始材料保留，恢复写入条件后可按原快照重新生成；失败不产生交付目录。

文件名变量只允许上下文字段的受控子集，不支持表达式。统一处理非法字符、保留名称、路径长度和文件名冲突。同名组追加稳定短标识，不覆盖另一人的文件。

## 9. 各输出类型的完整能力

### 9.1 Word 模板

采用 `docxtpl` 作为打印组件的模板渲染依赖，结合现有 `python-docx` 做模板结构检查。`docxtpl` 支持变量及专用于段落、表格行的标记；普通标记存在 Word run 边界限制。开发样例应使用其明确支持的写法，并开启 XML 自动转义。依据见 [docxtpl 官方文档](https://docxtpl.readthedocs.io/en/latest/)。

Tidoc 定义其受限子集：变量、指定集合的 `for`、`if/elif/else`、布尔比较、`loop.index` 和白名单格式化过滤器。支持正文、表格、页眉页脚中的上述结构；静态样式、分页、表头重复和图片由模板本身控制。

允许过滤器为 `money`、`number`、`date`、`default`、`join` 和 `upper_rmb`。人民币大写仅格式化人民币金额，不提供汇率能力。求和、单价和金额选择由核心完成，不在模板中运行任意运算。

禁止模板导入、动态 include、宏、赋值、函数调用、对象方法、任意属性遍历、原始 XML、子文档、网络资源和模板自行打开文件。未定义变量立即报错；可选字段由上下文提供 `null` 或空值，模板显式选择显示方式。

采用 Jinja 的受限环境并增加语法树白名单，传入纯数据且清空非白名单全局对象。受限环境本身不能防止资源耗尽，因此还要限制输入规模和渲染时间。依据见 [Jinja Sandbox 官方文档](https://jinja.palletsprojects.com/en/stable/sandbox/)。

模板检查覆盖所有参与渲染的 XML 部件，经过与渲染器相同的结构标记预处理后检查语法。报告模板文件、段落或表格位置、错误变量和修正建议。对拆散或格式不支持的标记给出错误，不尝试跨任意 run 猜测修复。

不承诺生成文件在 Word、WPS、LibreOffice 中像素完全一致。验收要求内容正确、没有占位符残留、表格不缺行、中文字体有回退方案，且代表性模板经过实际办公软件查看。DOCX 不自动转 PDF，不引入 Office 常驻进程。

### 9.2 材料 PDF

支持按条目连续排列或按材料角色排列；角色顺序由包声明，文件内部页序保持不变。自定义 PDF、实物图和付款图片使用同一材料资源接口。

图片支持 A4 纵向／横向、每页 1／2／4 张、固定边距、保持比例、自动适配方向。不得裁掉图像内容。付款截图继续保留张数和每张的完整可读区域。

原 PDF 页面默认保持尺寸，编号在输出副本上叠加。编号样式由有限枚举选择，包括现有 `No.<条目>-<页码>/<总页数>`。不开放任意坐标脚本或逐页水印语言。

输出要求的附件若为不可转换格式，在预检中阻止该 PDF 输出，并提示使用附件整理包保留原文件。禁止静默漏掉必需材料。

### 9.3 总览 Excel

由现有核心 OXML 写出器扩展，继续无需安装打印组件。支持单工作表、条目行或明细行、列 ID、显示标题、宽度、文字／日期／金额格式、冻结表头、筛选和末尾合计。

列来源使用与模板一致的字段目录。合计只允许核心定义的 `sum`、`count`，由十进制计算写入结果，不让包注入 Excel 公式。用户字符串始终作为文字写入。

每张发票的实付值不能在展开的每一条明细中参与重复求和。明细表将发票级金额只显示于该发票首行，或明确标为非合计列；合计取唯一发票集合。

### 9.4 附件整理包与输出清单

支持按抬头、报账人、条目形成目录，按角色选择附件和命名，保留原扩展名。路径变量只支持既定字段；不得将字段中的 `/` 或 `..` 解释为任意目录结构。

统一清单包含条目关联、材料角色、文件名和缺项说明。收款信息默认不写进清单。原有通用附件导出保留为内置输出配置，不另造第二套附件打包器。

`.tidoc` 属于交换协议，不是可自由定制输出类型。适配包只能提供默认的备注、标签和自定义字段带出选项，不能修改其文件结构与校验机制。

## 10. 数据归属、修订与历史稳定性

### 10.1 修订固定在条目上

每个条目保存 `scheme_id` 和 `scheme_revision_id`。前者确定本地方案及收款映射，后者固定规则定义。两个本地副本可以共享同一修订，但不能因此共用收款默认值或附加信息。

修订包含已经合成的抬头、字段定义、材料规则、设置策略和输出定义，引用不可变模板资源。修订不包含真实收款值、云服务密钥、机器路径和临时导出值。

更换默认方案只影响新条目。新导入文件的上下文按“导入预览明确选择 → 目标批次的新建默认修订 → 应用默认方案修订”决定。已有条目补充 XML、付款截图或云识别结果时仍使用自己的修订。

修改方案设置或升级适配包形成新修订。用户可以明确选择将新修订应用于某些旧条目，预览显示状态变化、缺项、字段和材料映射，以及哪些批次受到影响。重绑定按一个事务执行并记录历史，不自动改写发票事实。

条目规则变更日志与用户字段修改日志分别展示。规则重算不制造“用户修改了发票金额”的记录，也不改变当前“已修改”快捷筛选的含义。

### 10.2 批次与混合方案

批次保存一组新建默认方案 ID 和修订 ID，并允许引用其他方案或修订的已有条目。它不强制修改已加入条目的方案。单个条目仍只有一个所属批次。

批次字段按本地方案及适配包命名空间存储。导出混合批次时按本地方案、修订、抬头和输出附加分组拆开；每组只读自己的字段。普通 BITFSAE 批次只有一个修订，界面保持当前密度。

用户从多个批次勾选条目时，若输出依赖批次字段，必须按批次分组；未进批次的部分作为独立组，所需字段在本次导出中填写，不伪造一个永久批次。

### 10.3 字段或材料定义被删除

稳定 ID 的标签修改不会丢值。删除字段、移除选项、改变固定值或删除材料角色属于更新差异，导入预览必须显示。

旧修订和旧数据保留。用户显式将条目迁入新修订时，类型与 ID 兼容的值可以保留；无对应定义的内容进入只读“历史信息”。材料可以保留原角色标签，也可以由用户明确映射到新角色，不能删除附件或猜测语义相近的角色。

适配包升级不执行迁移脚本。跨 ID 映射由应用的重绑定预览完成，并保存映射结果；不加入第二套可编程转换协议。

### 10.4 状态缓存与失效

状态计算输入为“修订摘要、状态引擎版本、条目业务字段和附件角色计数”。缓存更新只覆盖受影响条目；切换默认方案不触发全库更新。

核心修正状态引擎时可以批量重算使用旧引擎版本的条目，必须沿用它们原来的修订。归档不会禁止修复缓存，但原导出快照和原交付文件保持不变。

抬头校验结论与识别事实分开。解析函数接收 `RecognitionContext` 提供候选抬头辅助，校验函数接收 `PolicyContext` 检查范围和税号。缓存指纹纳入会影响解析结果的候选上下文摘要，避免换方案后误用旧解析缓存。

## 11. 数据库存储与文件布局

### 11.1 新增表和字段

以下是逻辑表结构，实施时集中编写一份正式迁移。索引和外键必须随数据访问路径一起完成。

| 表／字段 | 主要内容 | 约束 |
| --- | --- | --- |
| `adapter_packages` | 包 ID、版本、内容摘要、格式版本、来源、验证状态、资源位置 | 包 ID 与版本唯一，摘要不可变 |
| `schemes` | 本地方案 ID、显示名、当前修订、是否默认、是否停用 | 最多一个应用默认方案 |
| `scheme_revisions` | 修订 ID、包摘要、规范化有效定义、创建时间 | 内容寻址，不就地修改 |
| `scheme_revision_links` | 本地方案与可用修订的关联 | 支持同一不可变修订被多个本地副本引用 |
| `payees` | 本地收款对象 ID、标准字段、创建与更新时间 | 账号按字符串保存 |
| `scheme_payee_links` | 方案默认收款对象、报账人到收款对象的映射 | 外键完整，删除前检查使用关系 |
| `extension_values` | 作用域、所属记录、包命名空间、字段 ID、类型化 JSON 值 | 复合唯一；仅允许指定作用域 |
| `extension_history` | 附加字段和规则重绑定的旧值、新值、操作身份与时间 | 与条目历史统一查询，避免无审计修改 |
| `export_jobs` | 任务状态、数据快照、修订引用、资源摘要、结果文件和诊断 | 任务完成后快照不可变 |
| `entries.scheme_id` | 条目所属本地方案 | 与修订组成关联约束 |
| `entries.scheme_revision_id` | 条目所用修订 | 外键指向有效修订 |
| `entries.title_profile_id` | 所选配置抬头 ID，可空 | 按条目修订检查，不覆盖票面购买方与税号 |
| `attachments.role_id` | 材料角色 | 以所属条目的修订解释 |
| `attachments.role_definition_revision_id` | 外部或历史角色的定义来源，可空 | 用于显示原角色，不自动满足目标方案要求 |
| `batches.default_scheme_id` | 批次新建条目默认方案 | 与默认修订成对保存 |
| `batches.default_revision_id` | 批次新建条目默认修订 | 不覆盖已有条目 |
| `entries.status_engine_version` | 持久化状态使用的核心引擎版本 | 用于有界重算 |

`extension_values` 的多作用域所属关系无法用一条普通外键表达。仓库层必须验证所属记录存在，并在删除条目、批次或收款对象的同一事务内清理对应值；增加孤儿检查测试。包命名空间不能由前端任意指定，必须从目标修订解析。

条目的 `(scheme_id, scheme_revision_id)` 使用复合外键引用 `scheme_revision_links`。批次默认引用同样成对检查。批次附加值包含 `scheme_id`，避免复制自同一包的两个本地方案误共用值。

保留 `entries.title` 作为已有展示兼容字段，已配置主体用 `title_profile_id` 明确关联。历史迁移按名称和已识别税号匹配；存在歧义时保持未匹配并提示，禁止只凭名称选第一个。改变默认抬头不会修改已有条目的购买方事实。

收款标准字段集中放在 `payees`，附加收款字段放在 `extension_values`。方案字段的实际填写值也放在 `extension_values`，不因为编辑一个部门编号而复制全部私人资料。

扩展值同时保存定义来源修订。字段被移除或外部定义暂不能采用时，仍能显示原标签、类型和值。来源修订随这些引用保留；仅展示历史信息的字段不参与当前规则计算。

字段定义和可分享默认值属于修订，实际填写值属于对应实体。普通导出使用实体当前值，导出任务保存当次值；重开旧导出只读任务快照。影响条目齐备的条件不能读取会变化的方案字段值。

### 11.2 数据目录

```text
<数据根目录>/
├── tidoc.sqlite
├── attachments/<entry_id>/
├── adapters/
│   ├── packages/<content_hash>/
│   ├── staging/<operation_id>/
│   └── imports/<operation_id>.json
├── export_jobs/<job_id>/
│   ├── context.json
│   ├── resources.json
│   └── result.json
├── exports/<job_id>/
├── components/
└── updates/
```

内置包发布于 `tidoc/builtin_adapters/`，启动时按摘要安装到数据目录。用户使用的数据副本不可变；核心升级携带的新包只增加可用版本，不覆盖旧资源。

`DataRoot` 的迁移、备份、恢复和失败回滚必须包含新增目录。有效路径全部通过 `DataRoot` 取得，禁止在模板中保存用户绝对路径。

### 11.3 文件与数据库的一致性

安装前将文件写入 staging，完成校验后移动到最终摘要目录，再提交数据库引用。移动完成而数据库未提交时仅产生未引用资源，后续清理可回收；不能先提交数据库再移动文件，避免形成失效引用。

保存操作日志并记录 staging、目标摘要和事务状态。失败时回滚数据库，保留仍被其他方案引用的资源；启动恢复只处理未完成操作，不重新执行用户确认过的业务导入。

删除方案只停用并隐藏入口。条目、任务或其他方案仍引用的修订和模板不得删除。真正清理采用引用检查，显示可回收空间后由用户触发。

### 11.4 导出记录与可重现范围

导出任务保存完整的当次标量数据、实际字段值、收款选择、模板摘要、规则修订、核心和组件版本。附件记录摘要与资源引用，不默默复制一份庞大的全库附件。

“查看原交付文件”读取已经保存的结果。“按原数据重新生成”使用任务快照，不读取今天的收款人、条目或方案默认值。模板资源由任务引用保留；附件已删除或内容变化时，说明缺失并阻止相关重生成，仍可打开未删除的原结果。

同一输入应产生语义一致的文档，不承诺跨渲染器版本的 ZIP 字节或分页完全一致。需要原样交付时以保存的原文件为准。清理导出记录时说明是否同时删除原输出，避免“清缓存”误删交付物。

## 12. 绑定包交换与身份兼容

### 12.1 协议扩展

绑定包写出版本为 5，继续读取版本 1～4。新增内容包括条目规则修订引用、必要的公共规则定义、自定义字段定义及可分享值、材料角色、扩展历史和来源标识。

新增规则、字段和来源数据全部纳入现有完整性校验清单。继续执行原有异常包确认和严重问题标记；不能因为规则来自可信名称的适配包，就跳过材料包本身的检查。

公共规则投影与本地完整修订分开计算摘要，并保存原始来源摘要。投影不包含收款对象、私人方案字段值、机器路径、OCR 密钥、打印任务和模板资源。接收方依据投影创建交换专用修订，不能拿同名版本冒充本机原包。

材料包默认携带足够解释条目齐备度的字段及规则定义。收款和个人设置只在本机输出预检中使用，不进入条目齐备规则。对 `transfer=ask` 的条目字段，导出预览列出字段名和记录数供用户决定。

`transfer=never` 的值、原值及历史值一起移除。若移除的是齐备检查所需值，接收方将它视为缺项，保留“发送方当时状态”仅供参考，不继承为本地已齐备。

条件引用的条目字段未带出时，接收方按三值逻辑得到待确定，不能把发送方的规则结果当作已满足。规则和模板本身不得含个人资料字面量；公共包导出按字段定义和范围筛选，无法从任意文案中自动识别所有个人信息，发布者仍需核对文案和静态模板。

### 12.2 未安装原包时的行为

接收方没有对应包时，也可以看发票、附件、字段和完整性检查结果。使用可解释的交换规则副本计算材料状态，方案入口显示来源说明，禁止自动安装或启用发件人的团队包。

需要原团队 Word 模板时，提示另行导入适配包。通用 Excel、附件整理和核心支持的材料 PDF 仍可用；不能用 BITFSAE 模板代替缺失模板。

交换规则需要当前核心不支持的能力时，保留原数据供查看与再次导出，状态显示“规则暂不支持”。禁止标记为齐备或伪造通过。基础材料接收不必被不可用的高级模板阻断。

### 12.3 重复材料和方案冲突

继续按现有发票号／文件摘要在全库判断重复条目。本次不创建多租户账套，不因适配包不同复制同一张发票。

包内条目命中本地已有条目时，保留本地修订。跨方案或不兼容材料角色的补充，在导入预览中显示差异，用户选择保留来源角色、映射角色或取消该条补充。自定义字段同 ID 同类型且命名空间一致时才按已有“本地非空优先”规则合并。

保留来源角色的附件记录其来源定义修订，出现在详情的历史／外部材料分组，仍可打开和通用导出。在用户明确映射并通过目标角色校验前，它不能满足目标方案的同名材料要求。

预览结果绑定材料包摘要、本地条目版本和所选修订摘要。确认前任一条件变化就重新预览；不能只检查材料包文件大小和修改时间后继续复用旧业务判断。

### 12.4 报账人与审核人

审核人可以为空，但名字必需。旧版本包继续按旧字段解析；不得因审核人为空把多个新报账人全部合并到当前身份。

同一来源包内用来源 ID 区分身份。跨包复用本机身份时：姓名与非空审核人完全一致可按现有规则复用；审核人为空且存在同名歧义时要求预览选择，不自动按名字合并。来源身份映射在一次导入内固定。

审核人必填要求在目标方案需要的操作上检查。允许先接收外部材料，再补负责人要求的信息，不能在导入阶段伪造审核人以通过校验。

### 12.5 老客户端兼容边界

新客户端继续读版本 1 至 4 的绑定包。旧客户端读取新包的能力不能由新代码保证，因此版本 5 不能宣称向旧客户端完全兼容。新包清单记录最低接收能力，导出界面提示旧版接收方需要更新。

本次不新增版本 4 降级导出器。旧格式不能表达方案归属，即使没有自定义字段，也无法保证按原规则解释条目。用户仍可导出通用 Excel 和附件 ZIP 供不使用新客户端的人查看；需要继续编辑完整材料时使用新版 `.tidoc`。

## 13. 安装、更新、复制与应用流程

### 13.1 导入适配包

导入过程为：读取包 → 校验归档 → 校验配置与引用 → 检查模板和能力 → 生成变更预览 → 用户确认安装 → 原子落库。

安装与设为默认是两个动作。首次使用时可以合并为“使用这个方案”，已有数据时默认只安装。导入窗口展示名称、作者、版本、主要材料要求、包含的输出和兼容情况，不展示大段 JSON。

选择 `.tidoc-preset` 的入口为设置、拖入应用和首次设置。拖入时必须识别为方案包，不能作为发票附件；本次不要求增加操作系统文件关联，也不扩展现有 `.tidoc` 的双击处理语义。

### 13.2 同包更新和本地覆盖

更新采用旧包定义、本地覆盖、新包定义的三方比较。未修改项采用新默认；用户明确修改项保留；新增固定值、字段删除、选项删除和冲突类型需要逐项解决。

界面显示“新增查验要求”“审核人改为必填”等业务变化，不只显示版本号。解决后创建新修订，并选择是否设为后续新建默认。既有条目不自动迁移。

更新来源只来自用户选择的本地文件或随核心发布的内置资源。本次不检查团队远程地址，不加入后台网络请求和自动包更新。

### 13.3 导出自己的方案

导出公共包时，合成公共设置覆盖，排除私人实际值、收款映射和本机偏好。导出预览列出将包含的抬头、规则、字段和模板，允许编辑名称、作者及说明。

用户没有修改定义，仅转发原包时保留其 ID、版本和摘要。导出经过本地修改的定义时必须创建新的包 ID，并记录来源 ID／版本用于说明；不能冒用原作者的相同版本。维护者在开发目录正式维护同一包时通过增加版本发布。

复制方案用于本机试改，不改变旧条目的引用。恢复某个设置默认值、回退方案当前修订和重新绑定旧条目是三个不同操作，按钮和反馈要分别说明影响范围。

## 14. 界面与操作行为

### 14.1 初次使用和默认方案

全新数据目录显示一次“选择报账方案”：通用、BITFSAE、导入方案。用户选择后直接进入创建报账人和发票导入，不经过配置向导长表单。

现有数据升级直接进入迁移后的方案，不再弹首次选择。正常只有一个方案时，主工具条不额外占一行；导入弹窗用紧凑说明显示当前方案。用户安装多个方案时，才提供默认方案切换。

通用方案采用中性文案，不默认填学校、税号和存放地点。它保留发票这一核心要求，其他材料可选；输出前按实际文件要求检查。未设置抬头时保留发票识别到的真实购买方，不自动套用北理工。

### 14.2 设置

“设置 → 报账方案”包含当前方案、选择方案、复制、导入、导出和查看包信息。日常设置展示普通选项；规则、字段和输出结构在只读详情中说明，复杂编辑由适配包源文件完成。

固定选项显示方案来源和简短原因；隐藏选项不占位置。个人收款信息继续有独立入口，避免用户把账号填进公共方案说明。

不建设可视化规则编程器、自由表单设计器或在线模板编辑器。开发者用编辑器和 Word/WPS 修改源文件，普通成员只需导入和填写。

### 14.3 条目、批次和打印

自定义条目字段在详情的“报账信息”区，保持字段声明顺序。缺项可从提示定位到对应输入；支持对同一字段定义和兼容修订的多条记录批量填写。

批次设置只显示相关字段。混合方案批次按方案分组显示字段，避免同名“项目编号”实际对应不同定义却共用一个输入框。

打印窗口从输出定义生成选项。仅为选中的输出要求必要字段；输出取消后不继续拦截无关必填项。日期和收款对象尽量沿用最近明确选择，实际采用值在生成前可见。

所有长操作立即显示当前阶段。安装包、应用修订或填写信息后，当前窗口立即刷新状态，不依赖关闭重开。

### 14.4 UI 实现范围

新增 `adapter-ui.js` 和 `schema-form.js` 管理方案展示与类型化字段，保留现有列表和对话框结构。只抽离被本次功能影响的代码，不以通用化为由重写整个 `app.js`。

共享前端字段组件处理标签、提示、输入类型、错误和焦点。后端负责最终配置解析和规则判断；前端不能维护另一份默认值或条件规则引擎。

不使用浏览器自动化、不创建模拟页面验证组件。通过源代码检查、纯函数测试和真实应用的人工操作核对界面；需要截图时只使用实际应用界面。

## 15. 核心与打印组件的稳定接口

### 15.1 对外公开接口的范围

适配作者依赖的公开接口只有包 Schema、设置／字段目录、规则语法、模板上下文和开发工具命令。Python 模块路径、数据库表、前端 API 和打印进程内部结构均不是第三方插件接口。

在核心内部设置 `AdapterService`、`PolicyEvaluator`、`ExportPlanner` 三个业务边界。它们不是需要安装或注册的插件对象，不提供事件总线和任意钩子。

```text
现有 UI / Api
    ├── AdapterService：包、方案、修订、字段表单描述
    ├── PolicyEvaluator：校验上下文、材料齐备、导出预检
    └── ExportPlanner：统一数据、分组、输出任务
            ├── 核心 Excel / 附件 ZIP
            └── 打印组件 DOCX / 材料 PDF
```

### 15.2 前后端操作接口

接口使用现有 `{ok, data, error}` 包装，新增结构化错误码但保留可读错误。下面是操作语义，实施时可统一命名风格，不向包作者承诺 Python 调用兼容。

| 操作 | 输入 | 结果 |
| --- | --- | --- |
| `list_schemes` | 是否包含停用项 | 方案、当前修订和可用能力 |
| `inspect_adapter` | 文件选择产生的本地路径 | 已验证预览 ID、摘要及差异 |
| `install_adapter` | 预览 ID、更新／复制选择、冲突解决 | 方案 ID 和修订 ID |
| `set_default_scheme` | 方案 ID | 新建默认值，影响范围说明 |
| `update_scheme_settings` | 方案 ID、原修订 ID、允许修改的设置 | 新修订和差异 |
| `preview_rebind` | 条目 ID、目标修订、映射 | 缺项变化与冲突 |
| `apply_rebind` | 预览 ID、确认版本 | 原子应用结果 |
| `get_form_description` | 作用域及所属记录 | 已解析的字段、值与展示规则 |
| `save_extension_values` | 目标记录、预期版本、字段值 | 验证结果和新状态 |
| `preview_export` | 条目、输出、收款选择、临时字段 | 任务计划、缺项、分组和摘要 |
| `run_export` | 计划 ID、期望输入版本 | 导出任务及进度 |
| `export_adapter` | 方案及公共导出选项 | 包预览与输出文件 |

预览 ID 由核心生成，只能引用本会话已经验证的数据。调用确认操作时重查包摘要或输入版本，处理用户在另一个窗口编辑造成的过期结果。

### 15.3 打印进程协议

增加独立能力查询入口，例如 `--capabilities`，返回 `ipc_versions`、`context_versions`、`renderers` 和 `adapter_capabilities`。查询只做本地检测，不联网。能力按组件文件摘要缓存，安装／更新后失效。

新协议请求包含 `ipc_version`、`job_id`、已冻结上下文、模板资源清单、计划文件和输出目录。组件不得访问核心数据库或重新选择方案；它只渲染已计划的输出。

源码模式和外部模式必须使用同一序列化协议、同一校验器和同一输出计划。源码调用不得通过 Python 对象绕过协议检查。

新打印组件继续识别当前旧格式请求，转换到内置 BITFSAE 兼容输出。新核心遇到只支持旧格式的组件时，对新方案的 DOCX/PDF 明确提示更新组件，不尝试把新配置塞进旧 `PrintOptions`。

核心 Excel、附件包和条目整理仍可使用。能力缺失只影响相关输出，不把整个方案标成无法使用。依赖安装和更新继续复用现有组件管理窗口。

## 16. 包资源检查与执行限制

### 16.1 归档与静态资源

包校验拒绝绝对路径、`..`、符号链接、重复路径、大小写冲突路径、路径规范化冲突、未声明文件和校验摘要不一致。只有 JSON、DOCX、PNG、JPEG 和纯文本说明能进入发布包。

未安装打印组件时，核心完成归档、JSON、引用和 DOCX 容器检查；模板语法与渲染验证标为待完成，相关输出不可执行。安装组件后自动完成本地验证并刷新状态，其他已验证功能始终可用。这里的自动验证不访问网络。

DOCX 按 ZIP 再检查一次。拒绝宏、ActiveX、OLE、外部模板、自动更新字段和外链图片；普通超链接只能保留为用户点击的链接，不在加载或渲染时访问。静态嵌入图片和样式允许保留。

内容摘要用于发现损坏和同版本冲突，不证明作者身份。软件不得把“哈希校验通过”写成“官方认证”。本次不新增包签名平台。

### 16.2 有界配置

协议默认限制为：单包压缩后 25 MiB、展开后 100 MiB、文件数 256、单个 JSON 2 MiB；字段总数 100、自定义材料角色 20、规则 100、输出 30。内嵌 DOCX 也计入解压预算。

单条规则表达式深度最多 8、节点最多 100。模板循环只遍历上下文中有界集合，最大嵌套深度 3，渲染任务默认超时 120 秒。实现必须支持取消及终止组件子进程，超时后不发布半成品。

这些限制由核心统一注册，用来防止配置误写和异常资源消耗。开发工具显示准确的超限位置，不能由包自身提高上限。金额和名称长度仍遵循各字段的具体校验。

## 17. BITFSAE 与已有数据迁移

### 17.1 内置包

交付两个真实内置包：`org.tidoc.generic` 和 `org.bitfsae.reimbursement`。二者走相同加载、校验、规则计算和渲染路径，核心不能包含“如果是 BITFSAE 就改走旧逻辑”的分支。

BITFSAE 包保留北理工和教育基金会的当前抬头及税号、原简称和语义色、学院、车队采购用途、工训楼、付款和查验要求、审核人要求、当前 PDF 排列与两份 Word 的默认输出。

原来从实际发票提取或用户核对的数据继续优先；模板参数不得反向填充发票事实。旧文案和模板表格可以保留外观，但内容来源改为标准上下文。

### 17.2 迁移识别与默认值读取

数据库迁移以实际旧配置为准，不根据某张发票的抬头猜用户团队。读取旧抬头列表、材料要求、默认抬头、实付初始化、输出偏好和收款信息；缺键时才采用旧程序的有效默认。

显式空抬头列表必须保留为空。旧 `localStorage` 中存在但 SQLite 没有的受影响业务偏好，通过一次前端迁移桥收集，再由后端验证保存；不读取主题或其他无关偏好。后台先完成数据库结构迁移，等待设置补齐前不开放新导入和打印，避免用一半旧值创建条目。

迁移结果为“原有报账方案”，来源记录 BITFSAE 内置基线和实际覆盖。已有条目统一指向迁移修订，已有批次保留原归属，设置新建默认修订。即使用户之前改成别的学校，也不会退回北理工。

### 17.3 旧收款信息迁移

完整或部分填写的 `tidoc.operator.*` 迁入一个独立收款对象；旧报账人中的可用收款字段分别迁入对应对象并建立映射。不得把部分统一信息与某个人的其余字段拼成新账户。

统一收款对象信息足够时直接作为迁移方案默认对象，现有 BITFSAE 操作不增加步骤。存在缺项或来源冲突时，仅在需要收款信息的输出预检中要求核对，发票导入和材料整理继续可用。

旧账号字段先保留只读兼容副本，不立即删除。迁移标志阻止重启后重复创建收款对象；旧写入入口改为转发新服务，不能继续产生两套互相覆盖的信息。

### 17.4 迁移事务、备份与回退

迁移前使用 SQLite 备份接口生成一致性备份，不能仅复制正在使用 WAL 的主数据库文件。外部资源安装先准备完成，数据库迁移在事务内更新结构、关联、状态和完成标志。

迁移按实际列和完成标志保持幂等。模拟中途退出、磁盘空间不足、备份失败和资源缺失，重新启动后应继续或恢复，不能留下无修订条目。

数据库版本从 11 升为 12。新代码明确拒绝写入比自身更新的数据库。旧二进制未必具备该检查，因此不承诺直接降级可用；回退必须恢复迁移前备份到独立目录，保留升级后新增数据供人工迁回。

### 17.5 行为兼容清单

必须保留：发票重复判断、已有材料、备注标签、实付修改历史、云识别记录、批次归档、单条与批量导入、抬头隔离、既有绑定包和组件更新入口。

允许明确修正：自动拼接不同来源的收款信息、从首条记录猜收款人、切换默认方案后重算无关历史条目。文档解释这些修正，在迁移样例中验证只在有歧义时增加一次核对。

## 18. 更新与兼容承诺

| 版本对象 | 用途 | 兼容规则 |
| --- | --- | --- |
| 核心版本 | 应用功能和修复 | 正常跟随主仓库发布 |

适配 API 1 的语义在支持期内固定。核心重构时通过转换器继续支持已经发布的 API 1 包；若未来必须引入新主版本，需要同时提供明确迁移说明和转换工具，不让作者跟着内部函数名变动。

每次核心发布运行所有内置包和代表性第三方样例的协议回归。独立打印组件的 CI 同时运行旧 IPC 和新 IPC 样例。版本号不是兼容性的替代品，不能仅比较“组件比某版本新”就假设能力齐全。

本轮工作区打印组件版本由 0.1.20 调整为 0.1.21，供后续发布通知旧组件更新。本次未构建、推送或发布该组件；真实成品和旧组件组合仍待验收。

新增资源必须加入 Windows 和 macOS 的打包配置、自检和安装后验证。核心升级保留整个数据目录，尤其是用户包、旧模板、修订和导出记录。

新增依赖只在实现代码实际导入时修改 `requirements*`。`docxtpl`、Jinja 及其模板相关依赖进入打印组件；核心与打印组件都实际使用 `jsonschema` 校验共享上下文，分别列入对应依赖清单。不要因写了计划提前修改依赖清单。

## 19. 开发者与 AI 辅助适配工具

### 19.1 命令行工具

提供 `python -m tidoc.adapter_tools`。开发环境可直接调用；不要求给最终用户另装 Python。普通用户的安装校验由桌面应用完成。

```bash
python -m tidoc.adapter_tools init ./my-team --from generic --id org.example.team
python -m tidoc.adapter_tools validate ./my-team
python -m tidoc.adapter_tools validate ./my-team --format json
python -m tidoc.adapter_tools explain ./my-team --fixture ./fixtures/basic.json
python -m tidoc.adapter_tools render ./my-team --fixture ./fixtures/basic.json --out ./preview-output
python -m tidoc.adapter_tools test ./my-team --cases ./cases
python -m tidoc.adapter_tools diff ./old-team ./my-team
python -m tidoc.adapter_tools pack ./my-team --out ./dist
```

`init` 生成完整、可校验的源目录。`validate` 检查结构、引用、模板和资源。`explain` 输出有效设置来源、条件判断过程、缺项及导出分组。`render` 使用真实渲染器和虚构数据生成实际文件，不生成模拟网页。

`test` 运行适配包声明的样例期望，包括文件数、分组、行数、金额及应有／不应有的文本。`diff` 区分文案、规则、字段和能力变化。`pack` 完成校验、排除开发文件、生成摘要和可复现目录顺序，遇到错误不得产出“可安装”的包。

工具退出码：0 表示通过，1 表示配置或样例失败，2 表示环境／依赖不可用。缺打印组件时 `validate` 报告“静态检查通过，模板渲染未验证”；`pack` 对含 DOCX 的发布包必须完成模板校验，不能把未验证包装成成功。

### 19.2 机器可读诊断

```json
{
  "ok": false,
```

### 21.2 BITFSAE 回归基线

用脱敏固定数据生成当前两份 Word 的语义基线：段落文案、表头、明细行、金额、人员字段、日期、存放地点和按抬头分组。基线不以整个 DOCX 二进制比较，因为时间戳和文档元数据可能变化。

PDF 基线验证材料页序、图片数量、横向 A4 两图布局和编号。Excel 验证原默认列和值。新机制必须保留当前实际物资名优先、历史缺明细安全补识别及实付差异提示。

代表性长表、长物资名称和多张付款截图要在 Windows 与 macOS 的真实应用中生成。人工打开产物核对版式，记录应用版本和使用的办公软件。不用浏览器自动化替代实际文档核对。

### 21.3 性能与资源预算

在同一开发机用固定数据记录改造前后耗时。数据集包括 10,000 条条目、每条平均 5 份附件元数据、5 个方案、20 条条件规则；实际大附件不放进版本库，由测试生成。

列表每页状态计算只读取相关修订并批量查询字段和计数，不能每张卡片重新读包、解析 Schema 或打开 DOCX。普通列表的中位耗时相对基线增幅目标不超过 20%，超出时先排查逐条查询和全库重算。

默认方案切换不得扫描全库。大包安装、迁移和导出有阶段进度，可取消的任务在完成当前有界工作单元后响应取消。性能记录注明硬件与数据量，不把某台机器的绝对耗时当作所有平台保证。
