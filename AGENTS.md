Tidoc product/design guidance learned from this project:
- Treat Tidoc as an operator tool for repeated reimbursement work. The primary path is invoice import -> material completion -> review/filter -> batch/export/print, so new UI should reduce movement along that path rather than add separate "feature pages".
- Keep one clear working surface. Prefer filters, presets, inline/card actions, context menus, and compact dialogs over duplicate navigation entries for the same reimbursement list.
- Put the most common material operations closest to the invoice card and detail header: attach payment screenshots, attach inspection files, mark paid amount, edit notes, batch select, export, and print. Low-frequency maintenance belongs under settings or advanced sections.
- Design for messy real inputs. Users may import PDF first, XML later or never, drag mixed files, batch by folder, fix recognition mistakes, and revisit incomplete material days later. Flows should make those states visible and recoverable.
- Keep flexibility concrete. Batch operations, tags, notes, drag/drop, right-click, double-click, and quick filters are valuable because they map to real operator shortcuts; avoid abstract customization that does not make reimbursement faster.
- User-facing text should help first-time users without sounding like implementation notes. Use terms like "打印导出组件", "材料", "报账批次", "检查更新"; avoid exposing dependency/package language unless it is in a troubleshooting-only path.
- Hints should be timely and dismissible. Do not show first-run guidance repeatedly after a user has acknowledged it; keep expert shortcuts discoverable through titles, subtle hints, and context menus.
- For update/install flows, keep state honest immediately after an action. If a component is installed, refresh the visible status in the same dialog and show an in-progress state while downloading, verifying, or installing.
- Network behavior should stay explicit unless intentionally changed. Today the app touches the network only for: online invoice verification, Aliyun OCR when the user clicks 云识别, opening external links, and update checks. The update check runs after startup (at most once an hour) and can be turned off in settings; downloading and installing only happen when the user clicks. Do not add other automatic background network activity without making the behavior clear in settings, and keep docs/guide/settings.md and docs/update/index.md in sync with this list.
- Visual hierarchy should stay quiet, dense, and useful: restrained blocks, clear grouping, small status badges, real data first, no decorative clutter, and no redundant images or copy that compete with the reimbursement work.
- The public documentation site lives in `docs/` (VitePress, served at https://tidoc.bitfsae.com). Its rules are in the "Documentation site" section below.
- Keep docs in sync with code in the same change. When code alters behavior, dependencies, status, or a documented flow, update the affected docs (README status list, DESIGN, CHANGELOG, docs/UPDATE.md, requirements*) as part of that change — do not leave them for later. Each fact has one authoritative home: implementation status lives in the README status list, design intent and architecture in DESIGN, release/ops detail in docs/UPDATE.md; other docs cross-reference rather than restate. Do not add a dependency to requirements* or DESIGN unless code actually imports it, and remove entries that code no longer uses.

Documentation site (`docs/`, VitePress, https://tidoc.bitfsae.com):
- Always remember the audience. Most readers are people who want to learn how to use Tidoc, or who are only finding out what it is. They do not know the internal logic, the code, or the project's internal vocabulary. Every page outside the 开发相关 section must be written for them, and every edit must be re-checked against this.
- Write from the reader's task ("我想导入发票"), not from the implementation. Say what to click, what they will see and what to do next. Name buttons and views exactly as the app shows them, in 「」.
- Do not leak internal terms into reader-facing pages: 修订, 快照, 重绑定, 方案修订, IPC, HMAC, manifest, context, schema, 适配包协议, 预检内部阶段, function/class names, database or file-layout details. Use the plain word instead ("方案改过之后，已有条目仍按创建时的规则处理"). When a product term is unavoidable (条目, 材料, 报账批次, 绑定包, 识别提醒), link its first use to the 基本概念 page. Technical wording is allowed only under 开发相关, and that section must say who it is for.
- Writing style: plain and concise engineering language; no commercial or internet-marketing wording; no absolute words (最、完全、绝对、100%); no self-praise or emotional wording; say why something works the way it does and what it brings; overview first, detail after; no "不是……而是……" constructions. Follow the tone of https://www.bitfsae.com/news/tidoc-guide: short imperative steps, no filler, no repetition.
- Do not state numbers, test counts, accuracy figures or comparisons that cannot be checked in the repository or were not supplied by the maintainer. State what the software does and the limits honestly (付款截图金额识别 is experimental; 阿里云 OCR is optional and paid).
- One fact has one home. User-facing usage lives only in the site pages; README keeps the status list and links; do not paste the same steps into several pages, link to them.
- SEO: every reader-facing page needs its own `description` (and a keyword-bearing `title` when the h1 is too generic) in frontmatter; pages without one fall back to their first paragraph. Sitemap, canonical links, Open Graph/Twitter cards and JSON-LD are generated in `docs/.vitepress/config.mts`; `docs/public/robots.txt` points at the sitemap and `docs/public/og-image.png` (1200×630) is the share image. A new page that should not be indexed must say so explicitly; do not add `noindex` to existing pages without being asked.
- Screenshots come from the real application running with fictional data only (no real invoices, names, tax IDs, account numbers or payment screenshots). Keep them in `docs/public/images/`, crop to the relevant area, and refresh them when the UI they show changes. The home page and concepts-page screenshots (`main-overview*.png`, `hero-cards*.png`) are regenerated with `python -m scripts.docs_screenshots` (needs Chrome or Edge and Pillow); it builds its own fictional data in a temporary directory, so extend `scripts/docs_screenshots/data.py` instead of capturing by hand.
- Changes to a documented flow update the matching site page in the same change. Build with `cd docs && npm ci && npm run build`; the build fails on dead links, so fix them rather than ignoring them.
- The Tencent EdgeOne side (project, domain, certificate) is configured by the maintainer, not in this repository beyond `docs/edgeone.json`.
